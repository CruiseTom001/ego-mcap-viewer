# MCAP 视频查看器（Windows 桌面版）

一个**原生桌面软件**：双击运行，出现程序窗口，选一个文件夹，就能把文件夹里的 `.mcap`
一个接一个顺着看完。列表里点哪个看哪个，看完当前会自动跳下一个。

不是网页，不需要开浏览器，不联网，不传数据。

---

## 快速开始

成品版直接双击 **`release\MCAP视频查看器.exe`**。这是约 95MB 的单文件程序，已经包含
Python、Qt、OpenCV 和 MCAP 依赖，不要求目标电脑安装 Python，也不需要首次联网下载。
单文件启动时需要解包到系统临时目录，通常会比源码版慢几秒。

如果要从源码启动，则双击 **`启动查看器.bat`**；第一次运行会自动建立 `runtime/` 并下载依赖。

1. 启动后按工具栏 **「📁 打开文件夹…」** 选中放着 `.mcap` 的目录
2. 程序自动读出文件夹里所有 `.mcap`（含子目录）并排好序；第一个自动解析并播放
3. **播完自动切到下一个**（可在工具栏关闭）。切下一个前会在后台预先把缓存做好

> 也可以把文件夹或 `.mcap` 文件直接拖进窗口，或者用命令行把路径当参数传入。

关闭方式：直接关窗口即可，程序不会在后台留进程。

桌面界面固定只创建并播放 **camera2、camera3** 两个主视角；camera0/1/4/5 不创建画面、
不启动播放解码线程，也不会出现在导出选择中。

## 环境要求

| 项目 | 要求 |
|---|---|
| 操作系统 | **64 位 Windows 10 1809（build 17763）或更高**；建议 Win10 22H2 / Windows 11 |
| 基础 Python | **64 位 Python 3.10 ~ 3.13**，推荐 3.12；仅用于首次创建 `runtime/` |
| 依赖 | 见 `requirements-win10.txt`，版本锁定且已验证 3.10~3.13 均有 win_amd64 wheel |

如果自动找不到 Python，在本目录新建 `python.txt`，写入一行 `python.exe` 的完整路径即可。

`runtime/` 是 Python 虚拟环境，不能从另一台电脑直接复制使用。发布软件时可不携带它：
启动器会在目标电脑的 `runtime.building-*` 中完整构建并验收，通过后才替换正式目录。
如果已有 runtime 损坏、来源电脑路径失效或依赖版本不一致，也会按同样方式自动恢复，
详细错误写入 `startup-error.log`。如果软件所在目录不可写，运行环境和启动日志会自动改放到
`%LOCALAPPDATA%\MCAPViewer\`，缓存也有相同的可写目录回退机制。

## 去畸变 + 参考框（构图比对）

Genrobot 采集规范要求画面构图满足：**双手尽量落在虚线区域内**，**人脸和第三人的手不得进入虚线区域**，
工人须在做当前任务。官方 Monitor 网页端里那条虚线是画在**去畸变后的画面**上的
（`Undistorted frame` 开关），本软件做了同样的两件事：

**① 去畸变** —— 勾选工具栏「去畸变」，把鱼眼画面拉直。
标定参数（K / D）就存在 mcap 的 `CameraCalibration` 消息里，**每段录像自带，不需要额外文件**。
实测与官方 Monitor 的 Undistorted frame 一致（显示器变方、货架垂直、桌沿变直）。

**② 参考框** —— 在去畸变画面上叠加**白色细虚线的圆角矩形**（四角以约 0.3 倍短边为半径过渡，
依据官方 Monitor 当前页面测得的近似区域），人工肉眼比对。首次打开默认使用：
`x=25%、y=13%、宽=50%、高=73%`，camera2/3 分别可拖拽微调。

| 操作 | 说明 |
|---|---|
| 勾选工具栏「去畸变」 | 鱼眼画面拉直；导出画面同样拉直 |
| 勾选「参考框」（或按 `R`） | 在画面上叠加参考框 |
| 「框形状」下拉 | 圆角矩形（默认，与官方一致）/ 椭圆 / 矩形 |
| 点「标定参考框」后**在画面上按住左键拖拽** | 画出一个新框，位置和大小以百分比实时显示 |
| 在画面上**点右键** | 清除当前相机的参考框，或清除全部 |
| 「应用到所有相机」 | 把当前相机的参考框复制给全部相机 |
| 「清除全部」 | 一键清空 |
| 「恢复默认框」 | camera2/3 恢复官网近似默认区域并立即显示 |

说明：

- 参考框按**相机通道**保存（`camera2` 一个、`camera3` 一个），记录的是**归一化坐标**，
  所以换文件、改窗口大小、切清晰度档位都不会漂。
- 同一台设备的同一路镜头，下次打开别的录像会**自动沿用**上次的参考框。
- 勾选「参考框」时**导出的画面也会把框一起画进去**，方便留证。
- **先开「去畸变」再标定参考框**：两种画面的坐标不通用，切换后要重新标一次。
- 去畸变的开销在解码线程里（800px 约 20ms/帧），画面落后时会自动显示最新可用帧，不卡界面。
- 它**只是人工比对的辅助线**，不做任何自动检测；要自动判定「手是否出框」需要接检测模型（B 档）。

## 支持范围（与实现严格一致）

### 容器

| 项目 | 支持情况 |
|---|---|
| MCAP 容器 | 使用官方 `mcap` 解析库 |
| 未分块、直接位于数据区的 Message | 支持 |
| Schema / Channel / Message 位于 Chunk 内 | 支持 |
| 没有 Summary / Statistics 的文件 | 支持，线性扫描自行统计条数与时长 |
| Chunk 压缩 | `none` / `zstd` / `lz4` 三种都支持 |
| Chunk CRC、DataEnd CRC | 非零时校验；不匹配会报错并给出文件偏移 |
| 记录长度异常 / 文件截断 | 报错并给出文件偏移，不会静默读空 |
| Channel `metadata` | 按 MCAP `Map<string,string>` 解析 |
| 消息编码 | `protobuf` / `ros1`（ROS1 二进制）/ `json` |

### 视频编码

| 编码 | 支持情况 |
|---|---|
| **H.264 / AVC**（Annex-B 裸流） | ✅ 完整支持。内置纯 Python 封装器**无损**装进 MP4（avc1 + avcC + 完整索引表），不重新编码 |
| **JPEG / PNG 逐帧图片** | ✅ 支持：按帧序列播放、定位、逐帧、导出 |
| **H.265 / HEVC** | ❌ 不支持。界面会明确显示「不支持该编码：h265」，不会送进 H.264 封装器 |
| **VP9 / AV1 / MPEG-4** | ❌ 不支持，同样给出明确提示 |
| 同一通道中途更换编码 | ❌ 明确报错（`该通道中途更换了编码格式：h264 → h265`），不会静默按第一帧格式处理 |

### 已识别的消息类型

- 视频：`foxglove.CompressedImage`（data=2 / format=3 / frame_id=4）、
  `foxglove.CompressedVideo`（frame_id=2 / data=3 / format=4）、
  `sensor_msgs/CompressedImage`（ROS1）——
  两种 foxglove 消息的字段号不同，程序**分开解析**。
- 数据：`foxglove.IMUMeasurement`、`sensor_msgs/Imu`、`foxglove.AudioData`（PCM）、
  `foxglove.CameraCalibration`、`foxglove.SystemInfo`

### 音频与 IMU 的多通道处理

文件里有**多路**音频或 IMU 通道时，程序**只使用第一路**，并把其余通道的 topic 记录在
manifest 里、在界面「通道说明」中标注出来。
**绝不会把采样率 / 声道数不同的音频拼进同一个 WAV。**

### 已知限制

| 限制 | 说明 |
|---|---|
| 单个 mdat 超过 4GB | 自动改用 largesize 头，可以正常工作 |
| 文件超过 4GB | chunk offset 自动改用 `co64`，可以正常工作 |
| 时长超过 32 位 | `mvhd`/`mdhd`/`tkhd` 自动改用 version 1（64 位时间字段） |
| 单文件总上限 | **256 GB**，超过会明确报错，不会写出损坏文件，也不会 `struct.pack` 崩溃 |
| 音频变速 | Windows MCI 的 waveaudio **不支持** `set speed`。程序会自动检测；速度不是 1× 时**自动静音音频**并在状态栏提示，回到 1× 自动恢复。**不会出现视频变速而音频仍 1× 的情况** |
| 音频格式 | 只处理 `PCM_16`（写入 WAV 交给系统播放），其它格式的音频会跳过 |
| 高倍速双路预览 | 2× 使用 60Hz 调度同步播放 camera2/3；5×/8× 时两路交替以约 30Hz 请求最新帧。双击任一路进入单路可进一步降低负载 |

时间轴拖动期间会把密集请求合并为最多 10 次/秒的预览解码，松手后只执行一次最终精确定位，
避免六路视频同时连续随机 seek。

## 时间轴同步机制

每条相机通道在缓存里都有一份**独立的逐帧时间戳**（`<key>.times`，float64 数组，单位秒，
基准是 manifest 的 `time_base_ns`）。取帧统一用

```
bisect_right(times, t) - 1     # 「不晚于当前主时钟的最后一帧」
```

- 相机**起点不同**：各路 `start_offset_s` 独立记录；时间轴还没走到某路首帧时，
  该画面显示「等待相机信号…」，不会提前显示首帧。
- **变帧率 / 中间丢帧**：直接按真实时间戳选帧，不依赖平均 fps。
- **首帧不是 IDR**：封装时丢弃前面无法解码的帧；`frames`、`frames_muxed`、
  时间戳数量、MP4 实际样本数**四者严格一致**，`start_offset_s` 取第一个**实际封装帧**的时间。
- 逐帧前进/后退、导出当前画面、多路合成，全部复用同一套选帧逻辑。

## 缓存

缓存目录 `cache/<file_id>/`，`file_id = sha1(绝对路径 + 文件大小 + mtime_ns)`。
`manifest.json` 里带 `cache_schema_version`；缓存结构变化时旧缓存判为**无效并重建**，
不会去删用户数据。

加载缓存前会校验：缓存版本 / 来源绝对路径 / 文件大小 / `mtime_ns` /
**所有声明的 MP4、raw、times、WAV、IMU 文件存在且非空**。任一项不通过就安全重建。

生成过程先写在 `*.staging` 临时目录，全部成功后才发布；`manifest.json` 最后一步用
临时文件 + `os.replace` 原子写入。同一文件同时只会有一个 prepare 任务在跑，
后台预热与前台打开会复用同一个任务。

### 精简缓存与 LRU 滚动清理

桌面版只把界面实际显示的 **视角 2/3（camera2/camera3）** 落盘成缓存，目录名是
`cache/<file_id>@desktop_camera2_camera3_v1/`，与 server.py 的完整缓存（无后缀目录、
全部相机通道）通过命名空间分离，同一份源文件的两套缓存可以共存；旧版无后缀缓存
会被自动纳入管理并随滚动清理自然淘汰。

* **最多保留 3 个**缓存条目（`appcache.MAX_CACHE_ENTRIES`），按 LRU（最久未使用）
  自动清理，打开第 4 个文件时最旧的被清掉。
* 台账文件 `cache/.cache_lru.json` 记录每个条目的最近使用时间与磁盘占用；
  台账丢失/损坏会自动重建，磁盘上未登记的缓存目录会被自动纳入管理。
* 保护规则（由实现保证）：**当前打开的文件、正在前台解析、正在后台预热的条目
  永不清理**；`.staging`/`.old`/`.tmp` 等进行中目录永不触碰；任何删除都限制在
  缓存根目录之内。
* 「当前文件」栏新增 **缓存策略 / 当前缓存 / 缓存占用** 三个字段；
  发生滚动清理时状态栏会提示清掉了哪些旧缓存。

## 常见问题

**Q：第一次打开很慢？**
A：第一次要把 H.264 裸流重新封装成 MP4 并建立索引。缓存生成后再打开是**秒开**。

**Q：为什么它要自己下载 Python 依赖？**
A：避免和系统里已有的 Python 环境（尤其是 Qt 库版本冲突）互相干扰。
程序在 `runtime/` 下自建**干净隔离**的环境，一次构建、永久可用。

**Q：复制到另一台 Win10 电脑后提示 runtime 无效？**
A：这是正常的，Python 虚拟环境本身不可移植。直接再次运行 `启动查看器.bat`，程序会用
目标电脑的 Python 3.10~3.13 x64 原子重建环境；不需要手工修改 `pyvenv.cfg`。

**Q：画面卡顿？**
A：把「解码」档位调低（例如「流畅 560px」），或关掉几路相机。

**Q：缓存占空间？**
A：大小约等于文件里视频数据的总和（raw + mp4 各一份）。整个 `cache/` 删掉即可，会自动重建。

**Q：数据会上传到网上吗？**
A：不会。程序完全在本机运行；只有第一次构建运行环境时需要联网下载依赖。
